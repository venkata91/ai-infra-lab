Phase 2 · Pretraining systems + scale

When one GPU is not enough

Frontier models do not fit in a single GPU. Training spans hundreds or thousands of accelerators talking to each other, surviving worker failures, and squeezing every last token-per-second out of the cluster.

Scope distributed training, sharding, checkpoint recovery, throughput, failure modes
Time · LOE 1–2 weeks · 12–16 hours
Deliverable modify the training stack to handle larger data and longer runs

Why distribute?

A single H100 has 80GB of memory. A 70B-parameter model in fp32 needs ~280GB just for the weights, before optimizer state, gradients, and activations. The math forces you across machines.

Data parallelism

Every GPU holds the full model. Each gets a different shard of the batch. After the backward pass, gradients are averaged across GPUs (all-reduce). Simple, but every GPU still needs to fit the model.

Tensor parallelism

Split a single layer’s weight matrix across GPUs. Each GPU computes a partial result; an all-reduce stitches them together. Lets the model itself be bigger than any one GPU.

Pipeline parallelism

Different GPUs hold different layers. Mini-batches are sliced into micro-batches and pipelined like an assembly line so all stages stay busy.

FSDP & ZeRO

Shard weights, gradients, and optimizer state across ranks. All-gather just-in-time when computing. Drops per-GPU memory by N× at the cost of communication.

Checkpointing & recovery

Long runs see worker failures routinely. Periodic checkpoints (weights + optimizer state + RNG + step) let you resume with minimal lost work. Sharded checkpoints save IO time.

Throughput & MFU

Model FLOP Utilization (MFU) measures how much of the GPU’s peak compute you’re actually using. 30–55% MFU is typical at scale. Most of the gap is communication, idle bubbles, and memory-bound ops.

Failure modes you will see

At scale, the question is not if something fails, but how gracefully you handle it.

  • OOM mid-step — activation memory spikes when sequence length, batch, or recompute config changes. Add gradient checkpointing or shrink batch.
  • Slow worker (straggler) — one GPU runs at 70%, the whole cluster waits. Watch step-time variance and isolate the host.
  • Silent NaN — loss spikes, gradients explode, weights become NaN. Add gradient clipping and loss-scaling sanity checks.
  • Network partition — collectives hang waiting for a peer. Set NCCL timeouts; design for clean restart from checkpoint.
  • Disk pressure — checkpoint writes back up, training pauses. Use async checkpointing and dedicated checkpoint storage.

Hands-on curriculum

Each checkpoint produces a concrete change to your training stack.

Checkpoint 1 · Single-node, multi-GPU DP

Take your nanoGPT-style training loop and run it across 2–4 GPUs with PyTorch DDP.

  • Exercise: wrap the model in DDP, set up torchrun.
  • Exercise: confirm gradient all-reduce works (gradients match across ranks before optimizer step).
  • Pass when: you can describe the all-reduce in plain English.

Checkpoint 2 · FSDP & activation checkpointing

Switch to FSDP, then add activation checkpointing to fit a bigger model.

  • Exercise: enable FSDP with full sharding.
  • Exercise: enable activation checkpointing on the transformer block.
  • Pass when: you can run a model that wouldn’t fit on a single GPU.

Checkpoint 3 · Robust checkpointing

Save and restore weights, optimizer, scheduler, and RNG state.

  • Exercise: implement async checkpoint save.
  • Exercise: kill the training mid-step; resume to within a few hundred steps.
  • Pass when: you can lose a worker without losing more than 1 checkpoint of progress.

Checkpoint 4 · Throughput tuning

Measure tokens/sec/GPU and improve it by 1.5× without changing model quality.

  • Exercise: profile one step with torch.profiler.
  • Exercise: try fused optimizer, mixed precision, and bigger micro-batches.
  • Pass when: you can name the bottleneck (compute / memory bandwidth / communication) for your config.
