Phase 3 · Inference fundamentals

Serving the trained model

Training is one model crunching a fixed dataset. Inference is one model crunching millions of unpredictable user requests. Different problem, different bottlenecks, different tools.

Scope serving architecture, latency, batching, KV cache, quantization, autoscaling
Time · LOE 1 week · 10–14 hours
Deliverable serve an open model and measure latency / throughput

Inference is not training

No backward pass, no gradients, no optimizer state. But you do generate one token at a time, and the cost compounds with sequence length.

Prefill vs decode

Prefill: all input tokens processed in parallel, compute-bound. Decode: each output token waits for the previous, memory-bandwidth-bound. The two phases need different tuning.

KV cache

Each generated token caches its keys and values so future tokens don’t recompute attention over the prefix. The cache grows linearly with context and is often the dominant memory consumer in production.

Continuous batching

Static batching wastes time waiting for the longest request. Continuous batching admits new requests every decode step and evicts finished ones, keeping the GPU saturated.

Quantization

Cut memory and bandwidth by storing weights in fewer bits. Modern int8 / int4 schemes (GPTQ, AWQ) keep quality close to fp16 while halving or quartering serving cost.

Latency vs throughput

Bigger batches finish more tokens per second but each user waits longer. TTFT (time to first token) and TPOT (time per output token) are the two latency numbers users feel.

Autoscaling

Add pods when queue depth or TTFT rises; drain pods when demand falls. Cold starts are painful: pre-warm replicas or accept a brief latency spike on scale-up.

Optimizations worth knowing

  • FlashAttention — fused attention kernel; lower memory, higher throughput, no quality cost.
  • Paged KV cache — vLLM’s trick: allocate KV memory in fixed-size blocks like OS paging, eliminating fragmentation.
  • Speculative decoding — a small “draft” model proposes K tokens, the big model verifies them in parallel. 2–3× speedup on memory-bound decode.
  • Tensor-parallel inference — same idea as TP in training, applied at serve time to fit larger models or shrink per-token latency.
  • Prefix caching — reuse the KV cache across requests that share a prefix (system prompt, RAG context).

Hands-on curriculum

Checkpoint 1 · Serve an open model

Stand up vLLM or TGI in front of a 7B-class open model.

  • Exercise: send 100 concurrent requests with curl or a benchmark tool.
  • Exercise: read the metrics endpoint.
  • Pass when: you can describe what TTFT and TPOT mean for your service.

Checkpoint 2 · KV cache & long context

Increase context length until you OOM. Find the wall.

  • Exercise: estimate KV cache size by hand (heads × head_dim × layers × tokens × 2 × bytes).
  • Exercise: enable paged KV cache and confirm fragmentation drops.
  • Pass when: you can predict OOM before it happens.

Checkpoint 3 · Quantization

Compare fp16, int8, and int4 (GPTQ or AWQ) on the same model.

  • Exercise: measure latency and quality at each precision.
  • Exercise: pick a target precision for your use case.
  • Pass when: you can argue for a specific precision with numbers.

Checkpoint 4 · Autoscaling under load

Wire your service into Kubernetes HPA or similar; benchmark a traffic ramp.

  • Exercise: trigger a scale-up; measure time-to-ready.
  • Exercise: tune HPA thresholds against latency SLOs.
  • Pass when: you can describe your cold-start strategy.
